Debugging Java for Beginners: How to Read Error Messages and Fix the Bug

By Syed Shahmikh Ali · Published 2026-11-16 · Updated 2026-11-16

Start with the error message, because Java usually tells you the exception type and the exact line where it happened. Read the first line for what went wrong, then find the first line of the trace that points at your own code, and that is where to look.

Key takeaways

  • A stack trace lists the methods that were running when the error happened. The first line names the exception, and the first line that mentions your own file is the place to start.
  • Compile errors come from javac before the program runs, and the caret marks where it got confused. Fix the first one and recompile.
  • ArrayIndexOutOfBoundsException means an index was negative or at least the array length. A loop condition with <= instead of < is a classic cause.
  • NullPointerException means you used a variable that holds null as if it were an object. Find where that variable should have been assigned.
  • If there is no error and the answer is wrong, you have a logic bug. Predict the output by hand first, then print the values and find the first line where reality and prediction differ.

What should you do first when a Java program fails?

Read the message from the top, slowly, before you change any code. Most beginners skim it, panic and start editing, which is how one bug turns into three. The message is information, and Java is usually specific about it.

There are three kinds of failure, and each needs a different response. A compile error means the code could not be built, so nothing ran. A runtime exception means it ran and then stopped with an error. A logic bug means it ran to the end and gave the wrong answer. The Oracle Java tutorial defines an exception as "an event, which occurs during the execution of a program, that disrupts the normal flow of the program's instructions." That covers the second kind. The other two are a typo-level mistake caught before running, and a mistake in your thinking that nothing catches for you.

How do you read a Java stack trace?

Read the first line for the exception type and message, then go down until you reach a line that names your own class and file. That line number is where to start. The lines below it show who called that method.

The Oracle tutorial describes the call stack as "the ordered list of methods that had been called to get to the method where the error occurred." A stack trace is a printout of that list. Here is a real one. I wrote a small Demo class with an average method, ran it on Java 21, and got this:

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
	at Demo.average(Demo.java:10)
	at Demo.main(Demo.java:24)

Reading it line by line:

  1. ArrayIndexOutOfBoundsException is the type of problem.
  2. Index 3 out of bounds for length 3 is the detail: the code asked for position 3 in an array that only has positions 0, 1 and 2.
  3. Demo.average(Demo.java:10) is where it happened: line 10 of Demo.java, inside the average method.
  4. Demo.main(Demo.java:24) is who called average. You only need this if line 10 looks correct and the real mistake is in what was passed in.

Longer programs produce longer traces, with several lines from library code you did not write. Skip those and look for your own file name. The wording of the detail message can differ between Java versions, so do not expect your output to match this text exactly.

What do compile errors tell you?

They give the file, the line, a short description, and a caret under the spot where the compiler got stuck. I wrote a two-line file with two deliberate mistakes and this is what javac printed:

Bad.java:5: error: incompatible types: String cannot be converted to int
        int x = "hello";
                ^
Bad.java:6: error: cannot find symbol
        System.out.println(y);
                           ^
  symbol:   variable y
  location: class Bad
2 errors

The first says you tried to put text in an int variable. The second says the name y was never declared. Two habits help. Fix the first error and recompile before touching the rest, because one mistake such as a missing brace can cause a long list of messages after it. And if the line the compiler points to looks fine, check the line just above it, since a missing semicolon or bracket is often reported on the line after the real mistake.

What do the two most common exceptions mean?

ArrayIndexOutOfBoundsException means you used a bad index, and NullPointerException means you used a variable that points at nothing. Between them they cover a large share of the crashes beginners hit.

ArrayIndexOutOfBoundsException. The Java documentation says it is thrown when an array is accessed with an illegal index, and that the index is either negative or greater than or equal to the size of the array (see the Java SE 17 API page). My crash above came from this loop:

for (int i = 0; i <= scores.length; i++)
{
    total += scores[i];
}

An array of length 3 has indexes 0 to 2, so <= lets i reach 3. The fix is i < scores.length. When you see this exception, check the loop condition and any + 1 or - 1 near the index first.

NullPointerException. The Java SE 21 API page lists the cases, including calling an instance method of a null object and accessing a field of a null object. Here is a class where a String field is declared but never given a value, so it holds null:

private String nickname;

public int nicknameLength()
{
    return nickname.length();
}

Running it on Java 21 printed Cannot invoke "String.length()" because "this.nickname" is null, followed by the line number. That message names the exact variable, which saves a lot of guessing. Your job is then to find out why nickname was never assigned: a constructor that forgot it, a method that was never called, or a value that came back empty from somewhere else.

How do you debug a program that runs but gives the wrong answer?

Predict the correct output by hand, then print values until you find the first place where the program disagrees with you. With no error message there is nothing to read, so you have to create the evidence yourself.

Here is an example I made up for this post. A method should count how many numbers are at least a limit:

public static int countBig(int[] nums, int limit)
{
    int count = 0;
    for (int n : nums)
    {
        if (n > limit)
        {
            count++;
        }
    }
    return count;
}

Called with {5, 10, 12} and a limit of 10, I expected 2 and the program printed 1. No exception, no warning. The prediction is what exposes it: 10 is at least 10, so it should count, and the condition uses > instead of >=. Adding System.out.println(n + " " + (n > limit)); inside the loop would have shown 10 false and pointed at the same line. Boundary values like this one, where the input equals the limit, are where many logic bugs hide, so always include one in your test data.

For longer methods, a trace table on paper does the same job: one column per variable, one row per loop pass. This is the same skill as tracing code in an exam, which I cover in my post on how to use past papers for computer science revision.

What is a repeatable process for fixing any bug?

Use the same five steps every time, so you are never guessing at random. The order matters more than the speed.

  1. Read the message. Note the type, the detail and the first line number in your own code.
  2. Look at that line and the one above it. Check the loop condition, the variable names and the brackets.
  3. Predict, then check. Say what each variable should hold at that point, then print them and compare.
  4. Change one thing. Make a single edit, rerun, and see whether the result changed in the way you expected. Several edits at once leave you not knowing which one worked.
  5. Test the edges. Rerun with an empty array, a single element, and a value equal to the limit.

If you are stuck for more than 15 minutes, write the problem down in one sentence: "I expected X at line Y but got Z." Writing that sentence often shows you the answer, and if it does not, it is exactly what to bring to a teacher. Frequently asked questions

Why does my Java error point to a line that looks correct?

The line number is where Java noticed the problem, not always where you made it. Check the line above for a missing semicolon or bracket, and for runtime errors check what values were passed into that line.

Should I use print statements or a debugger?

Start with print statements, because they work everywhere and make you think about what each value should be. A debugger that steps through code is worth learning once your programs have several methods, and it follows the same predict-then-check idea.

How do I stop making the same Java mistakes?

Keep a short list of your own errors with the cause and the fix, for example loop condition used <= instead of <. After a few weeks you will see that the same three or four mistakes repeat, and you will start checking for them before you run the code.
